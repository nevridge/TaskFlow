# Plan the day

Goal: agree a short focus list for a day (today unless the user says otherwise), then plan it in the journal.

1. Gather, calling tools in parallel where you can:
   - `get_journal` for the date (what is already planned and logged) and for the previous day (what was left unfinished). It lists the day's rows. A parent that has an open subtask planned that day appears as a `Context: #id title (not counted)` line with its subtasks indented beneath it; that line is not a planned task and is not in the "Planned tasks (N)" count. Subtasks that are not planned that day are not shown there; use `list_tasks` to see them. get_journal log lines for linked tasks read [task #id | Project | Priority], leave out the project when the task has none, show [task #id, deleted] for a deleted task and a bare [task #id] when the task could not be looked up, so read the project and priority from the line instead of calling list_tasks for them.
   - `list_tasks` with `view=overdue`, then `view=due_soon` (`dueWithinDays=3`), then `view=stale`, then `view=blocked`. To see tasks planned on a day other than the one get_journal already covers, call list_tasks with plannedDate=yyyy-MM-dd (or tomorrow, yesterday), adding view=all to include done tasks; do not call it for a day you already read with get_journal.
   - If the user named a project, pass `project` to those calls.
2. Propose a focus list of 3-7 tasks, most important first. For each: `#id title` and one short reason (overdue Nd, due soon, high priority, unblocks something). Say what is already planned (count each task once; a `Context:` line is not a planned task). Plan subtasks, not a parent that still has open subtasks: TaskFlow refuses to plan such a parent, so propose its open subtasks instead (find them with `list_tasks`). Do not pad the list to reach a number. Blocked tasks (flagged `blocked: <reason> (Nd)`) are not suggested for today unless the user asks.
3. List stale tasks (moved 3+ times) separately with one suggested decision each: do it today, re-scope, or drop. Do not change or delete them yourself.
   List Blocked tasks as their own group (`#id title`, reason, days blocked). If the wait may be over, offer to unblock with `update_task status=todo` (it restores the previous status, Todo or InProgress). Wait for a yes. If the user says another task is waiting on someone or something, propose `update_task status=blocked` with `blockedReason` (their words, max 200 characters) and wait for a yes. Do not log it with `add_log_entry`. Only Todo or InProgress tasks can be blocked: a Draft must be made Todo first, a Completed task reopened first. If they gave no reason, ask; never invent one.
4. Ask the user to confirm or adjust the list, and wait for the answer.
5. Once confirmed, call `set_journal_todos` with the agreed ids (`add`), and `remove` for anything they dropped. Report what is now planned. A single task can instead be planned with `update_task journalDate=today|tomorrow|yyyy-MM-dd` (the day must be today or later: `yesterday` is rejected locally and past dates by the API), and `journalDate` is separate from `dueDate`; use `set_journal_todos` for several tasks. To un-plan, use `set_journal_todos` with `remove`. A task that TaskFlow refuses to plan (open subtasks, or already completed) is reported on its own `x` line with what to do next; in a batch the other tasks are still planned, so relay the refusal and offer the subtasks. If the user also wants several tasks changed (re-date, unblock, re-prioritize), use one `update_tasks` call with an item per task instead of repeated `update_task` calls.

If nothing is overdue, due soon or high priority, say so and ask what they want to focus on.
